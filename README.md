## 核心结论（三句话）

1. **Grok Bot 值得抄的不是"一台云电脑"，而是它把 Agent 产品化的四层外壳**：对象模型（名册 / 技能 / 例行）、决策面（审查 / 审批 / 规则）、可见面（状态 / 面板 / 卡片）、触发面（定时 / 事件）。
2. **DSH 在这些层上不是更弱，而是更细但更散**：CUA 细到单应用单会话授权、审批有 `approval/asked → approval/decided` 审计事件、日志是完整 JSONL、沙箱是真隔离、模型可见可选。**缺的不是能力，是把能力聚成可被理解的面。**
3. **因此需求列表全是"装配"而不是"发明"**：19 条需求里 **15 条落在已存在的 DSH 服务上**，只有 4 条需要真正新建（围栏标记层、事件总线、实例注册表、表单卡片 kind），**没有一条需要云**。

## 三个 P0

| 编号 | 能力 | 为什么排第一 |
|---|---|---|
| R-A1 | **动作审计时间线** | 纯 Host 半、日志已有、Grok Bot 的等价能力是 Enterprise 专属 → 投入最小、差异化最大 |
| R-A2 | **审批收件箱** | Grok Bot 被社区骂了三个月都没做（"审批面要一个地方"）；DSH 已有 `approval/request` waterfall，缺的只是一个跨会话聚合视图 |
| R-B1 | **执行环境面板** | DSH 的 CUA + 沙箱 + 应用授权三套机制都成熟，但**散在三处**；聚起来就是 Grok Bot 的 Computer 区，而且比它更细 |

批次 0（R-A1 + R-A4 + R-A5）**纯 Host 半、零前端风险**，3–4 人日可交付，可作为前端工程链路的零风险验证替代。

**v1.1 的四个 P1（「一个小团队跑起来」的最小可用集，16 人日）**：

| 编号 | 能力 | 为什么是 P1 |
|---|---|---|
| G1 | **群聊消息族与投影**（`plugin:ops.chat` + `ops.chat` + ops tab 第五纵切页） | 用户最直接提的需求；且它是 G4/G5 的投影基座 |
| G2 | **Bot 角色装配**（preset 内挂 persona + 技能层 + 工具白名单） | 「每个 Bot 独立角色」的唯一正规入口；3 人日成本最低、收益最直观 |
| G4 | **团队名册与主 Bot 标记**（吸收 v1.0 的 C1） | 「主 Bot 统筹全局」的可见形态；只读投影，不抢 `dsh-agent-team` 的调度权 |
| G5 | **升级审批通道**（子 Bot 被拦 → 工单 → 根会话原生审批 → 主 Bot 重执行） | 补 DSH 唯一的架构硬伤（子代理永无审批权），也是与 Grok Bot 最大的行为差异 |

## 04 方案的一句话结论

**做窄而深**：只做"审计"这一件事，但做到"数据地基 + 三个视图 + 可导出 + 可编程消费"的完整度。

```
              会话日志（approval/asked · approval/decided · 工具事件）
                              │  session-projection（纯同步折叠）
                              ▼
                     ops.audit（审计脊柱）
                              │
        ┌─────────────┬───────┴───────┬──────────────┐
        ▼             ▼               ▼              ▼
   ① 审批收件箱   ② 审计时间线   ③ 执行环境     ④ 规则表/围栏
   （同一个右侧栏 tab 的三个纵切页）  （设置分区）  （guard + pre-execute）
```

三条硬差异（对 Grok Bot 而言是补它的坑，不是抄它的样）：

| # | Grok Bot 的做法 | 我们的做法 | 为什么赢 |
|---|---|---|---|
| 1 | 审批只在对话里弹，人不在场约 10 分钟过期变成 Expired | 保留 composer 接管，**另加只读收件箱** | 「没看见」和「看见时已过期」两个失败模式，它只解决一个 |
| 2 | Auto Review 只给结果不给理由；个人规则存在本机、换机重设、无命中统计 | 规则表 + **决策解释行** + 命中计数 | 安全评审的刚需；它的 Audit logs 是 Enterprise 专属 |
| 3 | 审计是 Enterprise 套餐的附加品 | 审计是**会话日志的投影** | 免费获得持久化、截断一致性与跨会话检索 |

工程上的关键判断：**全链路不需要一行 Typert Remote，也不需要自建 HTTP 路由** —— 读用 `useProjection`（官方 hook，9 个包在用），写用 `ctx.settings`，导出用现成的 deliverables 链路。16 条需求中 15 条落在已存在的 DSH 服务上，仅 4 个新骨架（围栏判定、规则存储、审计投影定义、表单卡片 kind）。

**v1.1 之后的部分为什么不是「第二个系统」**：群聊用 `plugin:ops.chat` 记录 + `ops.chat` 投影（不新建消息栈），名册用 `subagent/catalog`（不新建成员模型），升级审批用原生 `approval/request`（不新建审批引擎），示范学习用会话日志回放（不新建录制器）。判据（04 附录 D）：**能表达成「同一条日志上的新投影 + 新纵切页」就属于这条窄路**；需要新存储、新身份体系或新审批引擎就出界。

**v1.1 唯一的架构硬伤与应对**：`dsh-subagent` 的 `captureDelegatedPolicyOverrides()` 把**所有子代理的 approval 钉死为 `never`**（子代理系统提示词原文：operations that require approval are rejected automatically）。所以「子 Bot 遇到敏感节点请示」必须自建升级通道：`tools/pre-execute` 拦截 → `plugin:ops.escalation` 工单 → 根会话 `ctx.approval.request()` → 主 Bot 重执行。**任何设计只要指望子代理拿到审批权，就必然返工。**

里程碑：M0 骨架通了（1.5 人日）→ M1 账记上了（6.5）→ M2 看得见了，可对外演示（13.5）→ M3 说得清了，可交付（**22.5**，04 v1.1 已修正原文误写的 24.5）。

**v1.1 的两个里程碑**（见 04 §9.10 / §9.11）：M4 队伍拉起来了（+12 人日，累计 **34.5**）→ M5 团队守规矩了（+16 人日，累计 **50.5**）。全部 24 条净 **57.5 人日**（口径：C1 的 3 人日归入 G4，不重复计）。

## 一个必须说明的边界

**"排除云电脑"不等于"排除 Computer Use"。** 云电脑指的是厂商托管的远程持久化机器（Grok Bot 跑在 Cursor 云的 Firecracker microVM 上）；DSH 的 `dsh-cua` 是操作**用户自己这台电脑**的应用与窗口，两者在权限模型、审计、隔离性上完全不同。判定方法见 03 文档 §1.2 的四问判定树。
